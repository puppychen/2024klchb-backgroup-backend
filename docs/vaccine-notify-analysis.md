## 1. 資料儲存機制

### 1.1 同意旗標位置

疫苗施打通知同意**未獨立設表**，存在 `users.content` JSON 欄位內：

```json
{
  "name": "XXX",
  "phone": "09XXXXXXXX",
  "childes": [
    {
      "name": "小朋友姓名",
      "age": "6",
      "weight": "20",
      "birthDate": "2019-05-01",
      "primary_medical": "XX診所",
      "vaccineReminder": true
    }
  ]
}
```

### 1.2 相關資料表

| 資料表 | 用途 | 關鍵欄位 |
|--------|------|---------|
| `users` | 使用者主表 | `content` (jsonb) — 內含 `childes[].vaccineReminder` |
| `vaccines` | 疫苗定義（按月齡） | `id, name, months` — 共 18 種疫苗 |
| `vaccine_notifies` | 推送記錄 + 審計表 | `id, user_id, name, vaccine_name, months, birthday, notify_at` |

**注意**：此 SQL dump 中 `vaccine_notifies` 表**無資料**（只有 schema），因此無法從實際發送記錄統計。本分析採用推算邏輯。

## 4. 重要觀察與限制

### 4.1 `updated_at` 普遍集中在 2026-03 之後

2025-09~11 無已同意使用者。原因：`users.updated_at` 為「最後更新時戳」，每次使用者異動資料（如 LINE profile backfill、修改小朋友資訊）都會被覆蓋 → 實際「最早同意日期」無法從此欄位還原。

### 4.2 本推算為保守估計

若實際同意時間早於 `updated_at`，則 2025 下半年的通知量可能實際 > 0，上表為最小估計值。

### 4.3 推算 vs 實際發送的差異

| 維度 | 推算值 | 實際值（`vaccine_notifies`）|
|------|-------|----------|
| 資料依據 | `users.content` + `updated_at` | `notify_at` 時戳 |
| 精確度 | 受 updated_at 覆寫影響 | 100% 精確 |
| 本次 dump | 可算 | **無資料，無法算** |

## 5. 分析工具

分析腳本（可重複執行）：`/tmp/analyze_vaccine.py`

重新跑法：

```bash
uv run /tmp/analyze_vaccine.py
```

需處理：
- 13 個 `INSERT INTO users` 批次（總計 3,027 筆）
- JSON 中 SQL 單引號跳脫（`''` → `'`）
- `birthDate` 格式 `YYYY-MM-DD`
- 月齡計算需考慮日期早晚（早於生日那天的當月不算滿月）
